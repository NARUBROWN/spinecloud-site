# 아키텍처와 제공자

Spine Cloud는 CLI에서 배포를 접수하고 관리 API와 실행 에이전트를 통해 앱을 실행하는 구조입니다. 아래는 자체 예제 앱으로 검증한 구성과 로컬에서 준비 중인 변경의 설명입니다. 오픈 베타에서의 최종 구성은 배포 전에 확인해야 합니다.

이 그림은 자체 예제 검증에서 사용한 논리적 경로입니다. 각 구성 요소의 배치와 접근 정책은 실제 배포 설정에 따라 달라질 수 있습니다.

## 구성 요소

| 구성 요소 | 역할 | 기록된 환경 |
| --- | --- | --- |
| Spine CLI | 계정 연결, 앱 빌드와 배포 요청 | 사용자 개발 환경의 Preview 기반 개발 CLI |
| 대시보드 | 계정 승인, 앱과 배포 이력 확인 | Vercel의 React 웹 앱 |
| 관리 API | 인증과 소유권 확인, 배포 작업과 상태 관리 | Railway |
| 인증과 저장소 | 계정 인증, 메타데이터와 비공개 결과물 저장 | Supabase |
| 실행 에이전트 | 작업 조회, 결과물 검증, 앱 실행과 상태 보고 | Oracle Cloud Infrastructure의 VM |
| Portal 릴레이와 터널 | 공개 HTTPS 요청을 실행 앱으로 전달 | 자체 운영 구성 |

이 제공자 목록은 프로젝트 기록에 근거한 검증 환경입니다. 오픈 베타의 최종 리전, 데이터 위치와 제공자별 책임 범위는 아직 이 문서에서 확정하지 않았습니다.

## 배포 흐름

1. 사용자는 브라우저에서 일회용 코드를 승인해 CLI와 계정을 연결합니다.
2. CLI에서 `spine deploy`를 실행하면 앱을 선택하고 빌드 결과물의 배포를 요청합니다.
3. 관리 API는 계정과 앱 소유권, 결과물 형식을 확인하고 암호화한 결과물을 비공개 저장소에 보관합니다.
4. OCI 에이전트는 인증된 HTTPS 요청으로 작업을 조회하고 선점합니다. 결과물을 복호화한 뒤 해시와 형식을 확인하고 앱을 시작합니다.
5. 내부 상태 확인과 공개 HTTPS 경로를 확인한 뒤 배포 결과와 주소를 기록합니다.

위 흐름은 지정된 자체 예제 앱에 대해 실제 CLI, Railway, Supabase, OCI, Portal을 연결해 검증했습니다. 이 결과를 임의의 고객 앱에 대한 검증으로 확대할 수는 없습니다.

## 요청 경로와 선택 이유

방문자의 요청은 Portal 릴레이와 터널을 거쳐 실행 앱으로 전달됩니다. 에이전트는 관리 API에 직접 HTTPS 요청을 보내 작업을 조회하므로 OCI에 별도 인바운드 관리 포트를 추가하지 않습니다. 기존 환경에서 직접 SSH 연결이 시간 초과되어 이 방식을 선택했습니다. 시간 초과의 원인은 확정하지 않았습니다.

초기 구성은 단일 VM을 사용합니다. 운영 구성을 단순하게 만들 수 있지만 VM 장애가 에이전트와 실행 앱, 같은 서버에 놓인 릴레이 구성 요소에 함께 영향을 줄 수 있습니다. 고가용성이나 무중단 배포는 검증된 보장이 아닙니다.

## 개발자가 확인할 사항

- CLI가 요청을 접수한 상태와 앱의 실행 성공은 다릅니다. 배포 결과와 공개 경로 확인까지 살펴보세요.
- 앱은 내부 상태 확인 경로를 제공해야 합니다. 자체 예제의 확인 경로는 `GET /health`입니다. 일반 앱의 정확한 계약은 오픈 베타 전에 확정해야 합니다.
- `spine deploy`는 현재 Preview 기반 개발 CLI의 검증 흐름입니다. 설치 버전과 지원 플랫폼은 베타 공개 전에 안내해야 합니다.
- 데이터베이스 연결, 비밀값 갱신, 앱 로그에 민감 정보가 기록될 가능성은 앱 개발자가 함께 고려해야 합니다.
