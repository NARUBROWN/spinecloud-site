# 운영과 복구

Spine Cloud의 상태 표시, 자원 제한과 복구 방식은 앱이 실제로 어떻게 동작하는지 이해하는 데 중요합니다. 이 문서는 현재 기록과 운영 전 검증이 필요한 경계를 설명합니다.

## 상태와 관측

로컬 구현의 인스턴스 상세 화면은 에이전트가 보고한 서비스 상태, 내부 상태 확인과 공개 주소 상태를 구분합니다. 보고가 오래됐거나 시각을 신뢰할 수 없으면 현재 상태와 사용률을 표시하지 않도록 설계했습니다. 배포 성공이 현재 실행 상태를 보장하지는 않습니다.

로컬 구현은 앱의 최근 실행 로그를 수집합니다. 새 측정값을 저장할 때 오래된 측정값을 삭제하지만 수집이 멈추면 자동 삭제도 멈춥니다. 따라서 정해진 시간에 데이터가 삭제된다고 보장할 수 없습니다. 독립적인 만료 작업과 최종 보관 정책은 운영 전에 결정해야 합니다.

## 자원 정책

32 MiB 기준과 64 MiB 하드 한도, 기준 초과 시 연속 30초 제한은 로컬에서 구현한 정책입니다. QEMU의 Ubuntu ARM64 VM에서 systemd 자격 증명 전달과 제한 동작을 시험했습니다. 이 결과는 실제 OCI 전체 배포 경로나 여러 고객 앱의 동시 부하를 검증한 결과가 아닙니다. 정책은 운영에 아직 적용되지 않았으며 성능이나 용량을 보장하지 않습니다.

## 교체와 복구

로컬 구현은 새 배포의 내부 상태 확인이나 공개 연결이 실패할 때 이전 실행 파일과 설정을 복원하도록 설계됐습니다. 중단 후 재조정 로직도 격리된 테스트에서 확인했습니다. 실제 에이전트의 운영 서비스 교체, OCI 재부팅, Portal까지 이어지는 전체 복구는 아직 검증하지 않았습니다.

기존 배포의 실행 서비스 ID를 이력에 연결하는 마이그레이션은 기존 ID가 실제 실행 서비스 ID와 일치한다고 가정합니다. 운영 적용 전에 이 가정을 확인해야 합니다. 기존 앱과 결과물 허용 제한도 유지되고 있습니다.

## 서비스의 한계

단일 VM에서는 서버 장애가 여러 앱과 관련 구성 요소에 동시에 영향을 줄 수 있습니다. 백업 복원, 다중 사용자 격리, 다중 앱의 부하, 공개 인증서 갱신, 장애 대응 절차는 오픈 베타 전에 확인해야 합니다. 서비스 수준 목표, 복구 시간 목표와 데이터 보관 기간은 확정 후 공개합니다.
